# Firestore security model

## Who writes what

The web client performs **no** direct Firestore writes (verified: no `setDoc`/`updateDoc`/`addDoc`/`deleteDoc`/`writeBatch`/`runTransaction` anywhere under `src/`). Every mutation goes through the Worker (`worker/src/operations/*`), which verifies the ID token, checks role and sport scope, validates the input shape and the domain transition, writes atomically, and appends an audit entry.

**Important constraint:** the Worker calls Firestore with the *caller's own ID token*. Firestore therefore evaluates Worker writes as the calling admin, and rules cannot tell a Worker write from a hand-crafted one made with the same token. So the rules cannot be "deny all client writes". Instead each role is confined to the exact field-level envelope the Worker itself writes.

The Worker never calls Firestore's `beginTransaction`: Firestore refuses it for callers authenticated with a Firebase ID token (production returned `PERMISSION_DENIED` at that step). `beginTransaction()` therefore opens a local read set. Reads record each document's `updateTime`, and `commit` sends one atomic `documents:commit` whose writes carry `currentDocument` preconditions (`updateTime` for documents that were read, `exists: false` for documents read as absent or missing from a full-collection read). A concurrent change makes the commit fail as `ABORTED` and nothing is written.

## Envelope per collection

| Collection | Who may write | What the rules enforce |
|---|---|---|
| `fixtures` | create: Super Admin. update: Super Admin, or the sport's coordinator. delete: Super Admin, scaffolding only | `fixtureId`, `competitionId`, `matchConfigurationSnapshot` never change; `sportId` is set-once. Status may only follow DRAFT→SCHEDULED/COMPLETED, SCHEDULED→LIVE/COMPLETED/POSTPONED/CANCELLED, LIVE→COMPLETED/POSTPONED/CANCELLED, POSTPONED→SCHEDULED/LIVE/COMPLETED/CANCELLED, and, for the Super Admin only, COMPLETED→LIVE (reopen) and CANCELLED→SCHEDULED (reinstate). Leaving POSTPONED or CANCELLED clears `statusReason` and `resumeStatus`. `statusReason`/`resumeStatus` change only together with a postpone, resume or cancel: postponing records the status it came from, resuming must return to exactly that status and clears both fields, postponing and cancelling need a non-empty reason of at most 300 characters. Slots never change on a LIVE or COMPLETED fixture, for any role. Coordinators: only `status`, `statusReason`, `resumeStatus`, `slotA`, `slotB`, `scheduledDate`, `scheduledTime`, `venue`, `displaySummary`; only on DRAFT/SCHEDULED fixtures (a LIVE fixture may only change status and its lifecycle fields; a POSTPONED one may change status, lifecycle fields and its schedule); cannot publish (DRAFT→SCHEDULED); may complete a fixture only in the batch that records its result; **a slot may only change to the recorded winner of its feeder fixture** (feeder derived from round/matchNumber; it must advance into this fixture and side; the winner is read from the same batch's `matchStates` result). Super Admin may additionally overwrite or delete generation scaffolding (DRAFT, an auto-completed BYE fixture, or a SCHEDULED fixture that has no match state yet) so a bracket can be regenerated before play starts. The fixture update rule computes the document diff once and passes it to its helpers, which keeps large batches within the rules expression limit. |
| `matchStates` | Super Admin, or the fixture's sport coordinator | Keys limited to `fixtureId, scoringModel, version, data, result, penalties, history`; `history` is a list of at most 50 entries; `version` is exactly 1 on create and previous+1 on update; `data`, `scoringModel` and `history` change only while the fixture is LIVE before or after the batch (live scoring, undo, reopen); created for a LIVE/COMPLETED fixture, or for a SCHEDULED/POSTPONED one only when an early result type completes it in the same batch; `result.winnerSlot` is A/B. Coordinators may write a result only in the batch that completes the fixture, and only as `WALKOVER`, `RETIRED` (once play has started) or the scoring model named in the document; `DISQUALIFIED`, `ABANDONED`, `ADMIN_DECISION` and the older `ADMIN_OVERRIDE` are Super Admin only; **never deleted**. |
| `sports`, `competitions` | Super Admin | Any `matchConfiguration` change must raise `configVersion` (only the dedicated config operations do). `competitions.published` can only go false→true; a competition cannot be created already published. |
| `participants`, `teams` | Super Admin | `status` may only move ACTIVE→WITHDRAWN (`withdrawEntrant`); no way back, and none created as withdrawn. |
| `admins` | Super Admin | `email` must equal the document id; role/active/sportIds shape enforced; **delete is closed** (deactivate instead) so the "never zero active Super Admins" guard cannot be sidestepped. |
| `auditLogs` | create: any active admin; read: Super Admin | Append-only. `actorEmail` must equal the caller's verified email and `actorRole` (if present) their real role, so entries cannot be forged in another admin's name. Keys are whitelisted. No update, no delete. |
| `announcements` | Super Admin | unchanged |
| `siteContent` | create/update: Super Admin; read: anyone; **delete is closed** | Only the document ids `gallery`, `committee` and `details`. `gallery` holds only `items` (a list of at most 200), `committee` only `members` (a list of at most 100), `details` only `eventLabel`, `tagline`, `footerNote`, `heroTitle`, `contact` (a map); each also `updatedAt` and `updatedBy`. Item contents are validated by the Worker (`shared/schemas.ts`), which rules cannot express. Image bytes are not in Firestore: they live in the Worker's KV namespace and are served by `GET /media/{key}`. |

Any new Worker operation that writes outside these envelopes must extend the matching rule in the same change.

## Known limitations (not resolved here)

1. **Worker-only writes are not achievable with rules alone.** This includes `siteContent`: the Worker writes with the caller's token, so the rules must allow the Super Admin to write those three documents in the shapes above, and a hand-crafted Super Admin write is not distinguishable from the Worker's. Fully removing direct writes requires giving the Worker its own service-account credentials (a Worker secret, plus `allow write: if false` for clients). That is a deployment change that cannot be verified without a real project, so it was not made. The envelope above is the strongest confinement possible while the Worker forwards user tokens.
2. **Rules cannot query or read entrants.** `deleteEntity`'s "not referenced by any fixture" check, the "operational fixtures exist" locks, and "entrant is active / in scope" live in the Worker and the import validator only. A Super Admin (not a coordinator) writing directly could seat an arbitrary entrant in a DRAFT/SCHEDULED slot; the Worker never does, and coordinators cannot (their slot writes must equal the feeder's winner).
3. **Contact details are publicly readable.** `participants.phone` and `teams.captainPhone` sit in publicly readable documents because the public site reads those collections for names. Fixing this needs a data-model change (move contact details to an admin-only document); it is not a rules-only fix.
4. **Any active admin can append an audit entry** (as themselves, with their real role). Consequential entries are written by the Worker; a coordinator could add a misleading-but-correctly-attributed entry.
5. **Two layers of rules tests.**
   * `shared/firestoreRules.static.test.ts` (runs in `npm test`): a *textual* audit; it fails if a protective clause is removed but does not evaluate the rules.
   * `shared/firestoreRules.emulator.test.ts` (run with `npm run test:rules`, needs Java): 64 emulator-backed tests that replay every legitimate Worker write shape and the attacks above, including the cross-document slot rule (`get`/`getAfter`), early result types, reopen, reinstate and the score history limit. Run it after any rules change.
