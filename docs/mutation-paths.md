# Mutation paths by entity

Every write goes through a Worker operation (`worker/src/operations/*`) or, for image bytes only, the authenticated upload route; the web client has no direct Firestore writes. "SA" = Super Admin, "Coord" = sport coordinator (scoped to their `sportIds`). There is exactly one Super Admin. A coordinator can only schedule, start, score, undo, postpone, resume and complete fixtures of their own sports, and record walkovers and retirements for them; every other operation, including cancelling, reopening, reinstating and correcting a recorded result, is Super Admin only. Every operation below writes an audit entry (actor, role, operation, target, before/after, reason where required) except `updateLiveState`, which is not audited per tick; instead the match state keeps its last 50 previous scores in `history` with who saved each one and when.

## Fixture lifecycle (the one state machine)

```
            generateBracket                publishBracket              startMatch            completeMatch
 (none) ───────────────────▶ DRAFT ───────────────────────▶ SCHEDULED ───────────▶ LIVE ───────────────▶ COMPLETED
                               │  BYE fixtures are auto-COMPLETED     │                                     ▲   │
                               │  at generation (scaffolding)         └── early result (completeMatch) ─────┘   │
                               └── regenerate: until the first match starts             reopenMatch (SA) ◀──────┘
```
```
 SCHEDULED ──postponeFixture──▶ POSTPONED ──resumeFixture──▶ SCHEDULED
 LIVE      ──postponeFixture──▶ POSTPONED ──resumeFixture──▶ LIVE   (returns to the status it was postponed from)
 SCHEDULED | LIVE | POSTPONED ──cancelFixture──▶ CANCELLED
```
 SCHEDULED | LIVE | POSTPONED ──cancelFixture──▶ CANCELLED ──reinstateFixture (SA)──▶ SCHEDULED
```
COMPLETED can only go back to LIVE through `reopenMatch`, and CANCELLED back to SCHEDULED through `reinstateFixture`, both Super Admin only and both refused once a dependent later-round match has started. The legal transition matrix lives in `shared/fixtureLifecycle.ts` and is used by the Worker and the UI; the rules mirror it. Postponing and cancelling require a reason (stored as `statusReason`); postponing records `resumeStatus`, and resuming clears both fields. A postponed or cancelled fixture does not complete, so later rounds that depend on it wait; a cancelled one is flagged as needing action until it is reinstated and then played or decided. Scheduling (`saveFixture`) never changes status; resuming a postponed SCHEDULED fixture may supply a new date and time.

## Per entity

| Entity | Create | Update | Delete | Protected / guarded |
|---|---|---|---|---|
| **Sport** | `upsertEntity`, `commitImport` (SA) | `upsertEntity` (SA); `updateSportConfig` (SA) | `deleteEntity` (SA) | `matchConfiguration` only via `updateSportConfig` (versioned, scoring model must equal the sport's registered one; `upsertEntity`/import cannot touch it on an existing sport). `scoringModel` locked once any fixture exists for the sport. Delete refused while competitions reference it. |
| **Competition** | `upsertEntity`, `commitImport` (SA; never created published) | `upsertEntity` (SA); `updateCompetitionConfig` (SA); `publishBracket` (SA) | `deleteEntity` (SA) | `published` only moves false→true via `publishBracket` (also flips DRAFT fixtures to SCHEDULED); nothing unpublishes. `matchConfiguration` only via `updateCompetitionConfig` (versioned; locked once operational fixtures exist; scaffolding needs explicit acknowledgement then regeneration; participant type and scoring model must match). `sportId`/`participantType` locked once fixtures exist. Delete refused while fixtures, teams or participants reference it. |
| **Tournament configuration** (`tournamentConfiguration`) | with the competition | `upsertEntity` (SA) | with the competition | Distinct from match configuration. Only read at bracket generation, which is itself blocked once operational fixtures exist, so a later change cannot alter an existing bracket. `RANKING` seeding is rejected until a ranking source exists. |
| **Participant / Team (entrant)** | `upsertEntity`, `commitImport` (SA; roster validated against the effective configuration; phones normalised and unique per competition; team members must exist in the same competition and sit on one team only; pairs have exactly two members) | `upsertEntity`, `commitImport` (SA); `withdrawEntrant`, `withdrawEntrants` (SA) | `deleteEntity`, `deleteEntities`, `purgeCompetition` (SA) | `status` only ACTIVE→WITHDRAWN via `withdrawEntrant` (reason required, affected non-terminal fixtures reported, no auto-rebracket, audited); generic CRUD and import cannot change it. Delete refused if the entrant sits in any fixture's slotA **or** slotB. |
| **Fixture** | `generateBracket` (SA), `commitImport` (SA) | `saveFixture` (SA/Coord, DRAFT/SCHEDULED only, schedule fields only, a venue already booked at the same date and time is refused with `SCHEDULE_CONFLICT`, as is resuming into a booked slot); `publishBracket` (SA); `startMatch` (SA/Coord); `completeMatch` (SA/Coord; early result types also from SCHEDULED and POSTPONED); `correctResult`, `reopenMatch` (SA); `postponeFixture`, `resumeFixture` (SA/Coord, reason required for postpone, BYE fixtures refused); `cancelFixture` (SA, reason required); `reinstateFixture` (SA, reason required, optional new schedule); `generateBracket` (replaces scaffolding, including a published bracket until its first match starts; schedules are carried over; random draws store their draw number in the audit entry and keep same-college entrants apart in round one where possible); `commitImport` (SA; links each imported fixture to the next round; POSTPONED and CANCELLED are protected like LIVE and COMPLETED) | `generateBracket` and `purgeCompetition`, scaffolding only (DRAFT and auto-completed BYE) | Identity, topology (`nextFixtureId`/`nextSlot`) and `matchConfigurationSnapshot` never change after creation. Slots change only by winner propagation, which the Worker computes (clients never supply a slot). Entrants must exist, belong to the fixture's competition and sport, differ, and not be withdrawn before a start; a withdrawn entrant can never be recorded as a winner. Every propagation is checked against the shared bracket invariants (only newly introduced violations fail). Import: slot content validated (entrant exists/in scope/right kind/not withdrawn, winner slots follow their feeder), status changes refused (publishing belongs to `publishBracket`), merged result must satisfy the bracket invariants. |
| **Match state / Result** | `updateLiveState`, `completeMatch` (SA/Coord) | `updateLiveState` (LIVE only, optimistic `version`, previous score kept in `history`), `undoLiveState` (SA/Coord, restores the last saved score), `completeMatch`, `correctResult`, `reopenMatch` (SA) | none | `result` only via `completeMatch`/`correctResult`. A score completion (`decidedBy` = the fixture's scoring model) needs a recorded score that the shared rules (`shared/scoring/matchOutcome.ts`) say is finished, and the submitted winner must match it; the summary is computed from the score. Early endings use `WALKOVER`, `RETIRED`, `DISQUALIFIED`, `ABANDONED` or `ADMIN_DECISION` (`ADMIN_OVERRIDE` is still accepted): each needs a reason, kept in `result.reason` and the audit entry; coordinators may record walkovers (before or during play) and retirements (once play started), the rest is Super Admin only; walkovers, disqualifications and decisions are also allowed from SCHEDULED and POSTPONED. A walkover honors `walkoverBehavior` (`BOTH_ELIMINATED` is refused). Completion is refused with `NEXT_FIXTURE_NOT_OPEN` if the next-round match is already postponed, cancelled or played. `correctResult` is Super Admin only, refused once a dependent later-round fixture has started, finished, been postponed or cancelled, and records the new winner as an organisers' decision. `reopenMatch` returns a scored COMPLETED match to LIVE with its score, removes the result and resets the winner's next-round slot, under the same downstream condition. Live state must match the configured match length (tennis sets, cricket overs). |
| **Admin / coordinator** | `manageAdmin` (SA) | `manageAdmin` (SA) | none (deactivate) | Email/role validated; every assigned sport must exist; there is exactly one Super Admin: a second one cannot be created or promoted (`SINGLE_SUPER_ADMIN`) and the existing one cannot be demoted or deactivated (`SUPER_ADMIN_PROTECTED`). |
| **Audit log** | the operations above | none | none | Append-only; read by SA only. |
| **Announcement** | `createAnnouncement` (SA) | none via an operation | `deleteAnnouncement` (SA) | Length-validated; there is no edit. `deleteAnnouncement` removes one announcement in a transaction with an audit entry holding the removed document, and returns 404 `ANNOUNCEMENT_NOT_FOUND` for an unknown id. The rules still also let an SA edit/delete directly (the Worker is the only path the UI uses). |
| **Gallery** (`siteContent/gallery`) | `galleryAdd` (SA) | `galleryUpdate`, `gallerySetVisibility`, `galleryReorder` (SA) | `galleryDelete` (SA, one or many ids) | One document holding the ordered `items` list; array order is display order and `galleryReorder` replaces it in one atomic write (it must be a permutation of the current ids, otherwise `ORDER_MISMATCH`). Entries carry only the image, thumbnail, size, focal point and visibility; older stored keys such as caption or alt are dropped on the next write. Image and thumbnail urls must be uploads of kind gallery (`full` and `thumb` variants), and replacing an image together with its width and height is all-or-nothing. At most 200 items. Deleting an item or replacing its image deletes the old KV keys after the commit (best effort, logged on failure). |
| **Committee** (`siteContent/committee`) | `committeeAdd` (SA) | `committeeUpdate`, `committeeSetVisibility`, `committeeReorder`, `committeeRemovePhoto` (SA) | `committeeDelete` (SA, one or many ids) | One document holding the ordered `members` list, with the same ordering and cleanup rules as the gallery. Members carry name, designation (`role`), optional photo and focal point; older stored keys such as description are dropped on the next write. `photoUrl` must be an uploaded committee photo; `featured` replaces the old role-name heuristic. At most 100 members. |
| **Site details** (`siteContent/details`) | `detailsUpdate` (SA) | `detailsUpdate` (SA) | none | The whole document is replaced on each save; blank fields are dropped so the public site falls back to the static values in `src/config/siteContent.ts`. Fields: event label, tagline, footer note, hero title (screen-reader heading), contact email and phone (format-checked). |
| **Media upload** | `POST /api/media/upload?kind=&variant=` (SA, not an operation) | none | removed with the owning item | Authenticated, Super Admin only. The raw image body is accepted only if its magic bytes are JPEG, PNG or WebP (the declared content type is ignored), within a per-variant size limit, and stored in KV under a unique key. Reads are public through `GET /media/{key}` with immutable caching. An upload that is never attached to an item leaves an unused key. |

## Bulk data operations (SA only)

| Operation | What it does | Guards |
|---|---|---|
| `commitImport` | Writes in commits of at most 400 writes plus one audit entry each (max 25 commits). New participants, teams and fixtures are stamped with an `importBatchId` returned to the caller. Existing data is read only for the competitions named in the file. | New documents must not exist at commit time; a concurrent change returns `IMPORT_CONFLICT`; a failure after some commits returns `PARTIAL_COMMIT` and the same import can be re-run to finish. |
| `previewPurge` | Counts what a purge would remove, lists blockers, and returns a backup in the import format. Writes nothing. | Optional `importBatchId` narrows it to one import. |
| `purgeCompetition` | Deletes the competition's DRAFT fixtures, teams and participants (or one import batch). | Confirmation must equal the competition id. Blocked while any fixture is published, live or played, or an entrant is still seated or on a team that would remain. Queries are re-checked before the commit. At most 8000 documents per call; the rest is reported as `remaining`. |
| `deleteEntities` | Deletes selected participants or teams. | Seated or team-bound entrants are reported as blocked and kept. |
| `withdrawEntrants` | Withdraws many entrants with one reason. | Already withdrawn or unknown ids are skipped and reported; affected open fixtures are listed. |

## Where each invariant is enforced

| Invariant | Worker | Import validator | Firestore rules |
|---|---|---|---|
| Legal status transitions | per operation | status changes refused | `fixtureStatusChangeIsLegal` |
| No restart / reopen of COMPLETED, no revival of CANCELLED | `startMatch`, `completeMatch`, lifecycle operations | n/a | COMPLETED and CANCELLED have no outgoing transition; a POSTPONED fixture resumes only to the status it was postponed from |
| Slots only change by propagation | Worker computes slots | slot content + feeder convention + invariants | coordinators: slot must equal the feeder's recorded winner; nobody swaps entrants on a LIVE/COMPLETED fixture |
| Snapshot / identity / topology immutable | never written after creation | not writable | `fixtureImmutableFieldsUntouched` |
| Entrant valid, in scope, not withdrawn | `loadSeatedEntrant` | `checkImportFixtures` | not representable (rules cannot read entrants) |
| Dedicated-operation fields (`published`, entrant `status`, `matchConfiguration`) | `assertProtectedFieldsUnchanged` | `checkProtectedImportFields` | `published` false→true only, entrant status ACTIVE→WITHDRAWN only, `configVersion` must rise |
| Role and sport scope | `requireSuperAdmin` / `requireSportAccess` | SA only | `isSuperAdmin` / `isSportCoordinatorFor` |
| Deletions | dependents / slot references checked | n/a | only fixture scaffolding; match states, admins and audit logs never |
